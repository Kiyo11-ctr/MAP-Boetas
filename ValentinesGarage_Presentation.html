Assignment Requirements

Why This App Was Built

The Problem

  • Trucks arrive at Valentine's Garage with unknown prior damage — leading to false claims against the garage
  • Mechanics work on the same vehicle without knowing what others have already done, causing repeated or skipped tasks
  • Valentine (the owner) has no visibility into what each employee actually completed
  • Vehicles could be driven while in the garage — odometer misuse

The Three Core Requirements

① Truck Check-In
Capture registration, odometer km, and condition at arrival — permanently — so a baseline exists before any work begins.

② Collaborative Service Board
Mechanics tick off and write notes on tasks per vehicle. Every completion is attributed to a named mechanic.

③ Management Reports
Valentine sees what each employee did and the condition of every vehicle at check-in.

App Architecture

Three-Layer MVVM Architecture

Each layer has a single responsibility. No layer skips another. Dependencies only point downward.

🖥

UI Layer

Composable Screens + ViewModels
Renders state. Sends events up. Never talks to the database. Files: DashboardScreen, CheckInScreen, ServiceBoardScreen, ReportsScreen, EmployeesScreen + their ViewModels.

↓
🧠

Domain / Repository Layer

VehicleRepository + EmployeeRepository
Contains all business logic. Builds checklists, validates check-in data, assembles EmployeeReport objects. Sits between UI and Data.

↓
🗄

Data Layer

Room Database + DAOs + Models
Persists everything. VehicleDao, ServiceTaskDao, EmployeeDao. GarageDatabase. GarageConverters. Pure data access — zero business logic here.

Why this way?

Referenced directly from the course notes on Layered Architecture: each layer is independently testable, replaceable, and understandable.

MVVM = Model–View–ViewModel

Model = data classes + Room (Vehicle, ServiceTask, Employee)

View = Composable screens (pure functions that render state)

ViewModel = holds UI state as StateFlow, processes events, calls repository

Room Database — The Data Layer

GarageDatabase.kt

@Database(
    entities = [Vehicle::class,
                ServiceTask::class,
                Employee::class],
    version  = 1,
    exportSchema = false
)
@TypeConverters(GarageConverters::class)
abstract class GarageDatabase : RoomDatabase() {
    abstract fun vehicleDao(): VehicleDao
    abstract fun serviceTaskDao(): ServiceTaskDao
    abstract fun employeeDao(): EmployeeDao

    companion object {
        fun build(context: Context) =
            Room.databaseBuilder(
                context,
                GarageDatabase::class.java,
                "garage_db"
            ).build()
    }
}

GarageConverters.kt

// Room can only store primitives.
// Converters map our enums to Strings.
class GarageConverters {
  @TypeConverter
  fun condToStr(v: VehicleCondition) = v.name
  @TypeConverter
  fun strToCond(v: String) =
      VehicleCondition.valueOf(v)
  // ... one pair per enum type
}

Three Tables in the Database

vehicles   Stores every checked-in truck including odometerAtCheckin and conditionAtCheckin — these fields are never updated after insertion, forming a permanent audit record.

service_tasks   Each row is one checklist item. Foreign key → vehicleId (CASCADE DELETE). Stores completedByMechanicId — the audit trail for who did what.

employees   Mechanic/manager roster. Seeded on first launch. Referenced by tasks to attribute completed work.

Foreign Key CASCADE: when a vehicle is deleted, all its service tasks are automatically deleted too — no orphan records.

Data Layer

DAOs — Data Access Objects

Interfaces annotated with @Dao. Room generates the implementation at compile time. The UI never calls these directly — only repositories do.

@Dao
interface VehicleDao {

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insert(vehicle: Vehicle): Long

    @Update
    suspend fun update(vehicle: Vehicle)

    // @Transaction: fetches Vehicle + all its
    // ServiceTasks in one atomic DB operation
    @Transaction
    @Query("SELECT * FROM vehicles ORDER BY checkinDateTime DESC")
    fun getAllWithTasks(): Flow<List<VehicleWithTasks>>
}
@Dao
interface ServiceTaskDao {
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(tasks: List<ServiceTask>)

    @Update
    suspend fun update(task: ServiceTask)

    // Returns all tasks a specific mechanic
    // completed — used for Reports screen
    @Query("SELECT * FROM service_tasks WHERE completedByMechanicId = :mechanicId AND isCompleted = 1")
    fun getByMechanic(mechanicId: Int): Flow<List<ServiceTask>>
}

Key design decisions in the DAOs

suspend fun
All write operations are suspend functions — they run on a coroutine, off the main thread. Room enforces this: calling a suspend function from the main thread is a compile error.

Flow<T>
All read operations return Flow. This means every time the database changes, Room automatically re-emits the new data. The UI re-renders without polling.

@Transaction
getAllWithTasks() fetches vehicles AND their tasks atomically. Without this, the two queries could return inconsistent results if another thread writes between them.

Why not put queries directly in an Activity? See Slide 17 for the full answer.

Repository Layer

Repositories — Business Logic

Repositories are the only layer that talks to DAOs. They contain business logic the ViewModels should not know about.

@Singleton
class VehicleRepository @Inject constructor(
    private val vehicleDao     : VehicleDao,
    private val serviceTaskDao : ServiceTaskDao
) {
    // Exposes live stream — DB is the source of truth
    val allVehiclesWithTasks: Flow<List<VehicleWithTasks>> =
        vehicleDao.getAllWithTasks()

    // Business rule: odometer is PERMANENTLY recorded
    suspend fun checkInVehicle(...) {
        val id = vehicleDao.insert(Vehicle(...)).toInt()
        // Auto-create checklist based on condition
        serviceTaskDao.insertAll(
            buildChecklist(id, conditionAtCheckin)
        )
    }

    // Lambda used in buildChecklist:
    private fun buildChecklist(
        vehicleId: Int,
        condition: VehicleCondition
    ): List<ServiceTask> {
        val base = listOf(
            task(vehicleId, "Engine oil & filter", ENGINE),
            task(vehicleId, "Check tyre pressure", TYRES),
            // ... 6 more base tasks
        )
        val extra = when (condition) {
            CRITICAL -> listOf(
                task(vehicleId, "OBD-II diagnostic", DIAG),
                task(vehicleId, "Inspect injectors", ENGINE)
            )
            FAIR -> listOf(task(vehicleId, "OBD-II diagnostic", DIAG))
            GOOD -> emptyList()
        }
        return base + extra
    }
}

What business logic lives here?

Auto-checklist generation
When a truck is checked in, buildChecklist() creates 8 base tasks + up to 3 extra tasks depending on the vehicle's condition. A CRITICAL vehicle gets OBD diagnostics automatically added. This is business logic — it belongs in the repository, not in the UI.

Immutable check-in record
checkInVehicle() records the odometer and condition. There is no updateVehicle() that lets these fields be changed — the record is permanent by design.

EmployeeRepository.getEmployeeReports()
Assembles EmployeeReport objects by joining employee data with completed task data. The Reports screen just asks for this — it doesn't know how it's assembled.

@Singleton scope means Hilt creates one instance of each repository for the entire app lifetime. See Slide 10 for Singleton vs Scoped.

Hilt DI — DatabaseModule.kt

Instead of classes creating their own dependencies (tight coupling), Hilt injects them. This makes the code testable and modular.

// DatabaseModule.kt
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {

    // @Singleton = one instance for the whole app

        = db.vehicleDao()

    @Provides
    fun provideServiceTaskDao(db: GarageDatabase)
        = db.serviceTaskDao()

    @Provides
    fun provideEmployeeDao(db: GarageDatabase)
        = db.employeeDao()
}

Exam Question — DI Scopes

❓ "What is the difference between a Singleton and Scoped dependency? Which did you use? Show it in your code."

Singleton vs Scoped — Explained

@Singleton

One instance created for the entire application lifetime. The same object is reused every time it is injected anywhere in the app. Destroyed when the app process dies.

We used @Singleton for:

  • GarageDatabase — one DB connection for the whole app
  • VehicleRepository — shared state, one instance
  • EmployeeRepository — shared state, one instance
  • DatabaseSeeder — only needs to run once
// In DatabaseModule.kt:
@Provides @Singleton
fun provideDatabase(...): GarageDatabase

// In repositories:
@Singleton
class VehicleRepository @Inject constructor(...)

ViewModelScoped (Scoped)

One instance per ViewModel lifetime. Created when the ViewModel is created, destroyed when the ViewModel is cleared. Each screen gets its own scoped instance.

Our ViewModels are ViewModelScoped — Hilt's @HiltViewModel annotation handles this automatically. When you navigate away from a screen and its ViewModel is cleared, those scoped dependencies are also released.

// @HiltViewModel = ViewModelScoped by default
@HiltViewModel
class DashboardViewModel @Inject constructor(
    repo: VehicleRepository // Singleton injected in
) : ViewModel() { ... }

Why Singleton for repositories? The database is a shared resource. If two ViewModels had different repository instances, they could see different states. A Singleton ensures the same Flow is observed everywhere — one source of truth.

UI Layer

ViewModels — State Holders

❓ "What happens if the ViewModel is removed?"

@HiltViewModel
class CheckInViewModel @Inject constructor(
    private val vehicleRepo  : VehicleRepository,
    private val employeeRepo : EmployeeRepository
) : ViewModel() {

    // Private mutable state
    private val _state = MutableStateFlow(CheckInUiState())
    // Public read-only state
    val state: StateFlow<CheckInUiState> = _state.asStateFlow()

    fun submit() {
        val s  = _state.value
        val km = s.odometerKm.toIntOrNull()
        // Validate before calling repository
        when {
            s.registration.isBlank() -> { err("Reg required"); return }
            km == null || km <= 0    -> { err("Valid km required"); return }
            s.condition == null       -> { err("Select condition"); return }
        }
        viewModelScope.launch { // coroutine on main
            vehicleRepo.checkInVehicle(...)
        }
    }

    private fun err(msg: String) =
        _state.update { it.copy(error = msg) }
}

If ViewModel is removed — what breaks?

❌ Form state lost on rotation
Without ViewModel, all the text in the Check-In form (registration, odometer, condition) is destroyed when the screen rotates. ViewModel survives configuration changes.

❌ DB calls on the main thread
Without ViewModel + viewModelScope, you'd call the repository from the Activity's onCreate(). Room would crash with a "Cannot access database on the main thread" exception.

❌ No separation of concerns
All validation logic, all business rules, all state management would be dumped into the Composable or Activity — unmaintainable.

ViewModel survives: screen rotation, going back and forward in navigation, system killing background processes. The data stays. The coroutines have a proper scope. This is why it exists.

// How we expose state in every ViewModel:

// 1. Private MUTABLE — only ViewModel writes
private val _state =
    MutableStateFlow(DashboardUiState())

// 2. Public READ-ONLY — screens observe this
val uiState: StateFlow<DashboardUiState> =
    _state.asStateFlow()

// Alternative: convert a DB Flow directly
val uiState: StateFlow<DashboardUiState> =
    repo.allVehiclesWithTasks
        .map { DashboardUiState(vehicles = it) }
        .stateIn(
            scope    = viewModelScope,
            started  = SharingStarted.WhileSubscribed(5_000),
            initialValue = DashboardUiState()
        )

// In the Composable screen:
val state by vm.uiState.collectAsState()
// 'by' delegate means 'state' is a DashboardUiState
// Screen auto-recomposes when state changes

WhileSubscribed(5_000): upstream Flow stays active for 5 seconds after the last subscriber disappears. Prevents unnecessary work when switching screens, but resumes quickly if the user comes back.

❓ "What is a Lambda expression? Show me from your code."

Lambda Expressions — Everywhere

A lambda is an anonymous function — a function without a name, passed as a value. In Kotlin, lambdas are written inside { }.

In Repositories — .map { } and .filter { }

// Lambda: transform each VehicleWithTasks
// into a DashboardUiState
repo.allVehiclesWithTasks
    .map { vehicles ->  // ← lambda
        DashboardUiState(
            vehicles  = vehicles,
            isLoading = false
        )
    }

// Lambda: filter out managers
list.filter { e -> e.role != EmployeeRole.MANAGER }

// Lambda: count completed tasks
vt.tasks.count { it.isCompleted }

// Lambda: build distinct vehicle list
tasks.map { it.vehicleId }.distinct().size

// Lambda in buildChecklist:
val extra = when (condition) {
    CRITICAL -> listOf(
        task(vehicleId, "OBD-II scan", DIAG)
    )
    FAIR -> listOf(task(vehicleId, "OBD-II scan", DIAG))
    GOOD -> emptyList()
}

In ViewModels — .update { } and .launch { }

// Lambda: update state immutably
_state.update { it.copy(registration = v.uppercase()) }
//             ↑ 'it' = current state, lambda
//               returns the new state

// Lambda: coroutine body
viewModelScope.launch {
    vehicleRepo.checkInVehicle(...)
}

// In Compose screens — trailing lambda syntax:
Button(
    onClick = { vm.submit() } // ← lambda
) {
    Text("Complete Check-In") // ← trailing lambda
}

// Lambda with it shorthand:
LaunchedEffect(state.success) {
    state.success?.let {  // ← 'it' = success message
        snack.showSnackbar(it)
        vm.clearMessages()
    }
}

The trailing lambda syntax in Kotlin means if the last parameter of a function is a lambda, it can be written outside the parentheses. This is how all Composable layouts work: Column { ... } is a function call where the block { ... } is the trailing lambda.

Architecture Pattern

Unidirectional Data Flow (UDF)

State flows down from ViewModel to Screen. Events flow up from Screen to ViewModel. The screen never modifies state directly.

CheckInViewModel
StateFlow<CheckInUiState>
↓ .collectAsState()
↓ state flows DOWN ↓
CheckInScreen (Composable)
renders state, user types/taps
↑ events flow UP ↑
vm.onRegChange("N 4521 WH")
vm.submit() 
// CheckInScreen.kt — screen reads state down
val state by vm.state.collectAsState()

OutlinedTextField(
    // State flows DOWN — screen shows current value
    value         = state.registration,
    // Event flows UP — user types, VM updates state
    onValueChange = vm::onRegChange
)

Button(onClick = vm::submit) {
    Text("Complete Check-In")
}

// CheckInViewModel.kt — handles the event
fun onRegChange(v: String) =
    _state.update { it.copy(registration = v.uppercase()) }
// ↑ This triggers StateFlow emission
// ↑ Screen recomposes automatically
// Screen never modifies _state directly

Why UDF? There is only one place where state is modified (the ViewModel). This means you can always reason about what the screen will look like by looking at one object: the current UiState. No hidden state, no race conditions between UI components.

Exam Question — Single Source of Truth

❓ "What is the significance of having a Single Source of Truth and how is it reflected in your code?"

Single Source of Truth

What it means

There is exactly one place where data lives. All other parts of the app read from that one place. Nobody keeps their own copy.

In our app: the Room database is the single source of truth.

How it's reflected

// VehicleRepository exposes ONE Flow
// that every screen reads from:
val allVehiclesWithTasks: Flow<List<VehicleWithTasks>> =
    vehicleDao.getAllWithTasks()

// Dashboard reads it:
repo.allVehiclesWithTasks.map { ... }

// Service Board reads it:
repo.allVehiclesWithTasks.combine(...) { ... }

// Reports reads it:
combine(
    employeeRepo.getEmployeeReports(),
    vehicleRepo.allVehiclesWithTasks
) { rpts, veh -> ... }

What happens without it?

Problem: two screens cache their own lists
Dashboard has a list of 7 vehicles. ServiceBoard has a list of 7 vehicles. Mechanic completes a task on the Service Board. Dashboard still shows the old data. The user sees inconsistency.

Solution: Room + Flow
When a mechanic calls vm.completeTask(), it calls serviceTaskDao.update(). Room detects the change and re-emits the new data through getAllWithTasks() Flow. Both Dashboard and Service Board recompose simultaneously with the correct data — no manual refresh needed.

The check-in record is permanently immutable: odometerAtCheckin and conditionAtCheckin are written once and never updated. This makes the single source of truth trustworthy as an audit record — it is the ground truth for vehicle condition at arrival.

Exam Question — Circular Dependencies

❓ "How did you avoid circular dependencies between your modules or packages?"

Avoiding Circular Dependencies

Dependency Direction Rule

Dependencies only point in one direction: UI → Repository → DAO → Database. No layer imports from the layer above it.

ui.dashboard.DashboardViewModel
   ↓ imports
data.repository.VehicleRepository
   ↓ imports
data.local.VehicleDao
   ↓ imports
data.model.Vehicle

No arrows go back UP ↑
No layer knows about the layer above

❌ Circular = Repository imports ViewModel
This would mean: A needs B to start, B needs A to start → neither can start. Hilt would throw a compile-time error.

Package structure enforces this

// ✅ VehicleRepository only imports from
// data.local (below it) and data.model (below it)
import com.valentinesgarage.data.local.VehicleDao
import com.valentinesgarage.data.local.ServiceTaskDao
import com.valentinesgarage.data.model.*
// NO imports from ui.* — repository does NOT
// know about ViewModels or screens

// ✅ VehicleDao only imports from data.model
import com.valentinesgarage.data.model.Vehicle
import com.valentinesgarage.data.model.VehicleWithTasks
// NO imports from repository.* or ui.*

// ✅ data.model has NO imports from any
// other package in the project — it's the base

Hilt also enforces this at runtime: if you create a circular dependency (A → B → A), Hilt will throw a CyclicDependencyException at build time, not runtime. The dependency graph is validated when you compile.

di package is separate: The DatabaseModule and SeedModule live in their own di/ package. They know about both layers (they wire them together), but neither layer knows about di/. This is the Dependency Inversion Principle.

How coroutines are used

// 1. In ViewModels: viewModelScope.launch
// Runs on Main dispatcher by default

    // UI updates happen after this
}

// 2. Room DAOs: suspend functions
@Insert
suspend fun insert(v: Vehicle): Long
// suspend = can pause without blocking the thread
// Room automatically switches to IO dispatcher

// 3. In DatabaseSeeder: IO dispatcher
CoroutineScope(Dispatchers.IO).launch {
    if (employeeDao.count() == 0) {
        employeeDao.insertAll(defaultEmployees)
    }
}
// Dispatchers.IO = background thread pool
// for database and network operations

// 4. Flow.first() in EmployeeRepository
val tasks = serviceTaskDao
    .getByMechanic(emp.id).first()
// .first() = suspend, takes one emission

The Three Dispatchers

DispatcherUse case
Dispatchers.MainUI updates, viewModelScope default

Coroutine Test Dispatcher

// In unit tests, you replace the real
// dispatcher with a TestCoroutineDispatcher
// (or StandardTestDispatcher in newer coroutines)

// This makes coroutines run synchronously
// in tests — no timing issues

val testDispatcher = StandardTestDispatcher()

@Test
fun `valid odometer passes`() {
    // Our unit tests don't need a test dispatcher
    // because they test pure functions (no coroutines)
    assertTrue(validKm("128450"))
}
// A TestCoroutineDispatcher WOULD be needed
// if we tested ViewModel.submit() directly

TestCoroutineDispatcher / StandardTestDispatcher: in tests, coroutines run eagerly (synchronously). Without it, launch { } bodies may not execute before your assertions run, giving false test failures.
